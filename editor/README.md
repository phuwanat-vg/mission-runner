# Mission editor

Single-page web app for building `mission_runner` missions (JSON, schema
`mission/1`) without writing code. Vite 7 + TypeScript, vanilla DOM, no
runtime dependencies. The spec is in [`docs/editor-spec.md`](../docs/editor-spec.md).

## Run

```sh
cd editor
npm install          # dev dependencies only: vite, typescript, vitest
npm run dev          # http://localhost:5173 ; /api, /hooks and the WebSocket
                     # /api/events are proxied to http://localhost:8080
                     # (MISSION_API=http://host:port overrides the proxy target)
npm run build        # tsc --noEmit && vite build -> ../runner/mission_runner/webui/
npm run preview      # serve the built bundle locally
npm test             # vitest (round-trip of examples, validation, codegen)
```

A runner for development: `python -m mission_runner --sim` (see
[`docs/runner-api.md`](../docs/runner-api.md)). Without a runner the editor
works offline: editing, validation, drafts and export work; remote actions
are disabled with a tooltip and the status chip says "offline".

## How the runner serves it

`npm run build` writes `index.html` and `assets/` into
`runner/mission_runner/webui/` (`base: "./"`, so the paths are relative). The
runner serves that directory at `GET /`; if it is missing it falls back to its
minimal status page. The bundle contains no absolute URLs: the runner URL
defaults to `window.location.origin` when the page is served by the runner,
and to `http://localhost:8080` on the Vite dev/preview ports. Menu → "Runner
URL…" overrides it (stored in `localStorage`).

## Layout of the source

```
src/main.ts                bootstrap, HMR dispose
src/model/types.ts         TS mirror of mission.schema.json / sites.schema.json
src/model/blocks.ts        step + trigger registries (labels, params, summaries)
src/model/validate.ts      structural + semantic validation -> {errors, warnings}
src/model/expressions.ts   $ref / ${expr} detection, light syntax check, cron words
src/model/ids.ts           id generation, deep clone, step walking, path helpers
src/model/templates.ts     built-in "new mission" templates (the examples)
src/api/RunnerClient.ts    REST + WebSocket client with reconnect
src/state/Store.ts         document, selection, undo/redo, drafts, runner state, run marks
src/state/sha256.ts        SHA-256 (crypto.subtle is unavailable on plain http)
src/codegen/python.ts      mission -> nav2_simple_commander script
src/codegen/bt.ts          behavior_tree template -> Nav2 BT XML (mirrors bt.py)
src/ui/*.ts                panels; ui/dom.ts has the h() helper, ui/icons.ts the SVGs
test/*.test.ts             vitest; test/fixtures/*.xml are generated by bt.py
```

Regenerate a BT fixture with the reference generator (write bytes to keep LF):

```sh
../.venv/Scripts/python.exe -c "import sys,json; sys.path.insert(0, r'../runner'); from mission_runner.bt import render_behavior_tree; sys.stdout.buffer.write(render_behavior_tree(json.load(open(sys.argv[1]))).encode())" test/fixtures/navigate_with_recovery_default.json > test/fixtures/navigate_with_recovery_default.xml
```

## Decisions

Where the spec left room, the editor does this:

- **Dirty tracking uses the runner's `sha256`, not a local hash.** `PUT`
  returns the runner's sha256 and `GET /api/missions` lists it, so the editor
  records the server value at open/deploy and compares list values against it
  for the "Robot copy changed" banner. Local "modified" detection compares
  canonical JSON of the open document with the copy fetched at open, both
  produced in JS, so Python/JS float formatting differences (`1.0` vs `1`)
  never cause false positives. Editor-generated ids (`s_xxxxxx`, `t_…`,
  `i_…`) are stripped on both sides of that comparison, so a runner copy whose
  steps had no ids is still "up to date" right after opening.
  `sha256.ts` is kept for local use (drafts).
- **Drafts** are stored under `mission-editor.drafts.v1` keyed by mission
  name, only while the document differs from the runner copy; deploying (or
  discarding) removes the draft. A draft remembers the runner sha it was taken
  from, so reopening it after the robot copy changed shows the banner.
- **Rename** changes `name` in the document (undoable). The robot keeps the old
  copy until you deploy the renamed mission and delete the old one; the deploy
  chip shows "not on robot" for the new name until then.
- **Undo coalescing**: consecutive edits to the same field within 1.2 s form
  one undo step, so typing a word is undone at once. Structural changes always
  get their own step. The stack is 50 deep.
- **`value` fields** parse `12`, `true`, `null`, `{…}` and `[…]` as JSON and
  keep everything else as text; `"quoted"` forces text. Strings that start
  with `$` or contain `${` get an "expr" badge. Number fields that accept
  expressions (`numberOrExpr` in the schema) are text inputs.
- **Pose widget** stores a plain site name when no yaw override is given,
  `{site, yaw_deg}` with one, `{x, y, yaw_deg[, frame]}` for coordinates and a
  `$…` string for expressions. Editing an `[x, y]` point converts it to the
  object form; untouched points round-trip unchanged.
- **Inserting from the palette** puts the step after the selected step, into a
  selected empty `if`/`loop` container, or at the end of the flow.
- **Live marks** are cleared by `run.started` of the same mission or by the
  first edit after the run finished; edits during a run keep them.
- **Run with unsaved changes** asks "Deploy and run" / "Run robot copy" /
  "Cancel"; a mission that is not on the robot only offers "Deploy and run".
  Ctrl+S deploys.
- **STOP** stays clickable above modal dialogs (the button has a higher
  z-index than the backdrop) and posts `/api/stop` without confirmation.
- **Deploy errors** returned by the runner (`400 {errors}`) are shown in a
  dialog and merged into the badges until the next edit.
- **Sites panel** edits are local until "Save to robot" (`PUT /api/sites`);
  mission validation uses the local copy immediately. If the runner announces
  `sites.changed` while local edits are pending, the local copy is kept and a
  toast says so. Deleting a site from the panel deletes it from the active
  map only.
- **Python export**: the "Use robot pose" of `nav.follow_path` uses TF in the
  generated script (`robot_pose()`), templates in `behavior_tree` become a
  comment (export the XML separately and pass its path), and steps without an
  equivalent (`wait_event`, `modbus.*`, `gpio.*`, `http.request`,
  `run_mission`, `ros.call_action`, `ros.set_param`) emit a marked `# TODO`
  block with the step JSON.
- **Menu → Export BT XML** requires a selected navigation step whose
  `behavior_tree` is a template; otherwise the item is disabled with a
  tooltip.
- Below 900 px the left column and the inspector become slide-over panels
  toggled from the top bar; Esc closes them.
- **Design pass 2 (less clutter).** The first version showed everything at
  once with equal weight; the second pass keeps every feature but changes
  the hierarchy: the sidebar is one list at a time (`Missions | Sites`
  segmented control, remembered in `localStorage`), the block palette is
  gone and every "add step" affordance opens a searchable block picker
  (search focused, arrow keys + Enter, entries still draggable), mission rows
  are title-only with a dot only while active, trigger chips show just the
  summary with policy and problems in the tooltip and a dot for problems,
  step rows are flat with hairlines, short summaries (no raw type name) and
  hover-only handles/actions, nested bodies sit behind a single left rule
  with an inline label, inspector help is hidden behind a "Show help" toggle
  (label tooltips otherwise), empty inputs/vars tables are one line, and the
  run log is a 28px bar with the last result that expands when a run starts
  (`mission-editor.runlog.open`). Globally: `--border` lowered to `#2a303b`,
  no uppercase/letter-spaced headers, `--panel-2` only on controls, one
  accent color plus red STOP and run-status colors, 8px row padding, calmer
  banners and toasts (left color bar instead of bright borders), and the
  runner URL moved from a chip into the ⋯ menu (an "offline" chip appears
  only when the runner is unreachable).

## Runner API notes

Things the editor uses that are not (fully) in `docs/runner-api.md`:

- `GET /api/missions` entries carry `state` (`running` / `queued` /
  `suspended` / `idle`), `trigger_problems: []` and, for files that failed to
  load, `errors: []`; the editor shows them but works without them.
- `PUT /api/missions/{name}` returns `{ok, name, version, sha256, warnings}`;
  the editor uses `sha256` and `version` when present.
- `GET /api/examples` returns the example mission documents themselves (a
  list of missions), not `{name, title}` summaries.
- The editor sends `{"type": "ping"}` every 20 s over the WebSocket and
  ignores `pong`.
